# 0035. The adapter-backed hooks skip user site-packages

## Status

Accepted (2026-10-17), by the operator. Extends ADR 0001's amendment
(`docs/adr/0001-guards-fail-closed-on-missing-dependencies.md`), which
isolated the guards' inline python3 parsers, to the hooks that run a module
of this package. Strengthens ADR 0028
(`docs/adr/0028-guard-mcp-passes-set-monitor-only-for-prs-the-session-opened.md`),
whose `set_monitor` deny check is one of them.

## Context

Four hooks run a module of this package with
`PYTHONPATH="$here/.." python3 -P -B -m trimtab.adapters.<module>`:
guard-mcp's `set_monitor` check (`pr_monitor check`), `pr-monitor-record.sh`
(`pr_monitor record`), `pr-body-check.sh` and `doctrine-drift.sh`. Each also
probes the interpreter first with `python3 -P -c ''`.

`-P` keeps the working directory off `sys.path`, but leaves user
site-packages on. Python executes every `.pth` file it finds there, at start
up, before the module runs. The default user site
(`~/.local/lib/python3.X/site-packages`) is writable by the session, since it
runs as the same user. A review of trimtab-core#89 found the gap. On
2026-10-17 a `.pth` that prints `pass` and exits 0 made guard-mcp pass
`set_monitor` for a PR the session never created. That is ADR 0028's deny
check failing open. The same plant can write a session's PR list from inside
the recorder, and runs inside the other two hooks.

These four cannot simply take `-I`, as the inline parsers did: `-I` ignores
`PYTHONPATH`, which is how they find the package.

## Decision

Every interpreter these four hooks start runs with `-s` (no user
site-packages) as well as `-P`, the version probes included:

- `python3 -P -s -c ''` for the probes;
- `PYTHONPATH="$here/.." python3 -P -s -B -m trimtab.adapters.<module>` for
  the runs.

Nothing else changes. The modules use only the standard library and this
package.

## Options considered

- **`-I`, with the package path put on `sys.path` by a `-c` bootstrap and
  `runpy`.** Rejected. It also shuts out every `PYTHON*` variable, but those
  come from the environment Claude Code starts the hook in, which the
  session does not set. It adds the same few lines of bootstrap to four
  hooks for that.
- **`-E` with `-s`.** Rejected. `-E` drops `PYTHONPATH` too, so it has the
  same problem as `-I`.
- **`site.ENABLE_USER_SITE = False` set inside the modules.** Rejected. A
  `.pth` runs before any module code, so it is too late.
- **Leave it.** Rejected by the operator: it lets the session forge the
  `set_monitor` verdict and the recorder's list.

## Trial

On 2026-10-17 `tests/guard-tests.sh` gained a plant: a `.pth` in a user site
under `$CPTMP`, with `PYTHONUSERBASE` pointing the interpreter there instead
of at the real one. It writes a mark file whenever it is loaded, and with
`US_FORGE` set it also prints `pass` and exits 0.

- Against the hooks on `main` (9fd16a1), the four "does not run" cases
  failed, because the mark was written. The forged case also failed:
  guard-mcp printed nothing, so it passed `set_monitor` on a foreign PR.
- With `-s`, all five pass.
- A fixture case shows that the plant does load into `python3 -P` without
  `-s`, so the passes come from the flag and not from a dead plant.
- An earlier draft exported the plant's variables to the whole test. The
  harness's own python3 then loaded the plant, and the forged case failed
  for the wrong reason. The variables now go to the hook alone.

## Consequences

- A `.pth` in user site-packages no longer runs inside these four hooks, and
  cannot forge the `set_monitor` verdict or write the recorder's list from
  inside it.
- Anything an operator deliberately installed into user site-packages is no
  longer visible to these hooks. They need nothing from there.
- Not covered here:
  - `hooks/rule-usage.sh` runs `python3 -B "$dir/rule_usage.py"`, which also
    loads user site. It is an observer, so a plant there can only forge
    usage data, and it was outside the change the operator authorised.
  - `bin/env-names.sh` reads its script from stdin (`python3 -`), which also
    puts the working directory first on `sys.path`. The same review found it.
    guard-paths blocks every read of that file, which is the right policy for
    the inspector, so its fix is left to the operator.
