# 0022. No reference to the run in what it writes

## Status

Proposed (2026-10-13). Becomes accepted once a guarded cloud routine on a
base carrying both parts below opens a PR whose commits and body hold no
reference to the run (see "Trial, still open").

## Context

A routine, environment or session ID is never written into a file, PR, commit
or log: it names a credentialed object, and a routine is found by its rendered
name instead (the routines README). The scrub checks the base's own tree for
ID shapes; nothing checked what a run writes elsewhere.

The first guarded runs of the per-project routines did. Both PRs they opened
on a consumer, a conformance report (merged) and a structure draft (closed),
carried the run's session link three times:

- a `Claude-Session: https://claude.ai/code/session_…` trailer on the commit;
- the bare session URL on its own line after the PR body's last section;
- a `---` / `_Generated by [Claude Code](<session link>)_` footer that was not
  in the body the run wrote, so most likely added when the PR was published.

None of it came from the method or the prompt. Claude Code's documented
default attribution in cloud sessions adds the first two
(`attribution.sessionUrl`, default true); the third is undocumented. The
merged commit's trailer stays in the consumer's history: a merged commit is
not rewritten to remove it.

Documented constraints: an empty `attribution.commit` or `attribution.pr` does
not remove the link, `attribution.sessionUrl: false` does; a repository's
committed `.claude/settings.json` is not read in a multi-repository cloud
session (every per-project routine has two sources); CLAUDE.md is context,
not enforced configuration. Expected, not yet observed: a routine run reads
`attribution` from the settings the bootstrap installs. The guard hooks those
settings register fire there, which shows the file is read, not that every
key in it is honoured; the trial below settles it.

## Decision

Three parts, each catching what the one before it can miss:

- **The setting.** `settings.base.json` sets
  `"attribution": {"sessionUrl": false}`, so the installed settings stop the
  trailer and the URL line at their source. It is a security control (Claude
  Code settings), so it lands in a PR of its own, on the operator's named
  authorisation, not in this one.
- **The check.** `trimtab check-pr` refuses a body holding a routine,
  environment or session ID shape anywhere, the block or not, and names the
  line, never the value. A consumer's CI runs it on every PR, so a link the
  setting does not stop (the footer) fails there loudly. It is
  `prblock.check_pr_body`: `check_body` plus the ID scan. `check_body` is
  unchanged, so the PR-body hook (a control), `ingest` and `dependabot-block`
  behave as before. The ID shape moves from the scrub to `trimtab/ids.py`,
  shared by both, and now also covers `cse_` session IDs. It is narrowed to
  what an ID looks like: the tail after the prefix is 16 or more letters and
  digits that mix upper and lower case. Every routine, environment and
  session ID seen so far does: each tail is 24 characters, `01` and then 22
  letters and digits in both cases (two routines, one environment and one
  run's session, read 2026-10-12). An option name in one case
  (`env_` followed by a long upper-case name), as quoted release notes carry,
  does not match. A digit is not required: a random 22-character tail has none
  about one time in fifty, too often to miss. The miss rate below assumes the
  tail is random over all 62 letters and digits; if a single-case format
  appears, the lookaheads are dropped for its prefix. The shape is bounded by
  anything but a letter or digit, so an underscore beside an ID (Markdown
  italics) does not hide it. The narrowing is for text a run reads but did not
  write: a PR body and the content of a file it commits. Where no third party
  writes, `ANY_ID_SHAPE` keeps the broad shape, in either case: the scrub of
  the base's own tree and its deny-list of IDs read from the instance, the
  routine templates' tests, file names, and git's messages. There a missed
  ID costs more than a reworded word.
- **The rule.** The routine prompts and every command that commits or opens a
  PR say: no `Claude-Session:` trailer, no session link or ID; a commit ends at
  `Co-Authored-By:`, a PR body at its `🤖 Generated with` line; this overrides
  any default attribution. Before each commit, the run runs
  `trimtab ids --staged`, which asks git for what the index adds, copies,
  modifies or renames (NUL-separated, from the repository root, so any working
  directory and any path, UTF-8 or not, work, and a deletion-only commit has
  nothing to check) and runs the ID scan alone over each file and each file's
  name, with no block, lock or instance. It reads the content staged in the
  index, by object ID (`git ls-files --stage`, then `git cat-file blob`),
  which is what the commit records, not the working copy; a submodule entry
  has no content of its own and is skipped. git's own error text has any ID
  shape masked before it is shown, since git names the paths it could not use. A file's bytes are read with undecodable ones
  replaced, so a binary passes unless it holds an ID in plain text; a name
  that holds one is a finding shown by its position in a list the reader can
  reproduce (`git diff --cached --name-only`, or the arguments given), never
  printed; a name with a newline or escape sequence is shown quoted. `trimtab
  ids FILE…` checks named files the same way. It is its own subcommand, not a
  `check-pr` mode: it checks files, not a PR body, and a whole commit in one
  call. Static tests fail if a shipped file
  that opens a PR lacks the rule, if a copy of it drifts from the rest, or if
  a shipped file that commits lacks the file check.

The retro's structure step also loses its last GitHub search syntax
(`--search "… in:title …"`), which cloud sessions refuse (ADR 0021); it reuses
step 4's PR listing. A static test fails on search syntax in shipped files.

## Options considered

- **The prompt and command rule alone.** Rejected as the only control: text
  the model may weigh against a default it is also told, with nothing that
  fails when it loses. It stays as the third part.
- **The check inside `check_body`.** Rejected. It would change what the
  PR-body hook does (a control) in a code PR, and make `ingest` count past
  PRs whose bodies hold a link as invalid, rewriting coverage history.
- **A committed `.claude/settings.json` in each consumer.** Rejected. A
  multi-repository cloud session does not read it, and every per-project
  routine has two sources.
- **Server-managed settings.** Not taken: an organisation setting outside the
  base and the instance, invisible to their review. The operator may still
  set it.
- **A commit-message check in the consumer's CI.** Deferred: it is a change
  to the consumer's workflow (a control there), and the setting covers the
  trailer at its source.

## Consequences

- A PR body with a run reference fails `check-pr` locally and in a
  consumer's CI; the run or the operator removes the line.
- The check is not limited to routines. A PR an operator opens from any cloud
  or Remote Control session carries the session URL by default too, and fails
  a consumer's CI once its pin includes this change. So the setting is
  installed before, or with, the first pin that carries this check; until it
  is, the remedy is deleting the line from the body.
- Accepted: the check reads the whole body, text the project did not write
  included, such as a Dependabot PR's quoted release notes. A word there with
  an ID's shape fails the consumer's CI after `dependabot-block` has passed
  its own re-check (`check_body`); the CI gate has no override. The remedy is
  editing that line of the body, which holds only until Dependabot rewrites
  the body on its next rebase; a PR it keeps rebasing fails again each time,
  until it merges. The narrowed shape makes it rare.
- Accepted: in a PR body or a committed file's content, an ID whose tail
  happens to lack upper or lower case is missed; for a random tail of 22
  letters and digits that is about one in eighty thousand. The scrub, file
  names and git's messages use the broad shape and miss none. A mixed-case word after a prefix (`session_CookieSameSite…`)
  still matches, including inside a snake_case name, since an underscore
  before the prefix no longer hides it; that is the remaining false positive.
- Accepted: only the body is gated. A file a run commits is checked by the
  run itself (`trimtab ids`, a step the method prescribes, not a gate); the
  consumer's CI does not scan changed files, which would be a change to its
  workflow, a control there, and is deferred to it. A run reference in a PR
  title, or in an issue or PR comment a run posts, is covered by the prompt
  rule alone.
- The PR-body hook keeps `check_body`, so a local session's hook passes a body
  that a consumer's CI then fails. The hook adopts `check_pr_body` in its own
  control change.
- Accepted: commit messages are not checked by the base. Until the setting is
  installed, and if it fails, a trailer can still land; the scrub of the
  consumer's history (the operator's ID scan) is what finds it.
- Accepted: if the platform appends its footer after the PR is opened and the
  consumer's CI does not re-run on a body edit, the check does not see it.
  The routine prompt asks the run to report such a footer.
- Words like `env_file` or `session_url` pass: the shape needs 16 or more
  characters after the prefix.
- Accepted: `trimtab ids` reads each file whole, one git call per staged
  file, so a very large staged binary costs its size in memory, twice. The
  files a run commits are reports and rule text; streaming in chunks is left
  until a run stages something large.

## Trial, still open

After the setting and this change are both on the pinned base: one manual
run of a per-project routine that opens a PR. Its commit has no
`Claude-Session:` trailer, and its body, read back after publication, holds no
session link or footer. If the footer persists, record it here and report it
upstream.
