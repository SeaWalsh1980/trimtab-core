# 0024. A run reads back what it writes

## Status

Proposed (2026-10-14). Becomes accepted once a guarded cloud routine on a base
carrying this change opens a PR, `trimtab verify-body` exits 0, and the PR's
body, read afterwards, holds no reference to the run (see "Trial, still
open").

## Context

ADR 0022's trial (2026-10-14) ran a per-project routine on a base whose
installed settings carry `"attribution": {"sessionUrl": false}`. The commit
had no `Claude-Session:` trailer and the bare session URL line was gone, so
the setting was read. The PR body was not clean: after the body the run sent,
which ended at its `🤖 Generated with` line and passed `trimtab check-pr`,
GitHub held two more lines, a `---` rule and
`_Generated by [Claude Code](https://claude.ai/code/session_…)_`.

Claude Code's settings reference says `sessionUrl: false` also omits the link
in pull request descriptions. It did not omit this one, and no documented
setting names it: `attribution.pr` sets the line Claude Code writes, which the
run writes itself. Which component appends the footer is not documented. The
operator reported it upstream. A server-managed (organisation) setting is the
only documented route into a multi-repository cloud session, and nothing
documents it covering this footer either.

Every PR a run opens goes through `gh api` POST to `pulls`, which the PR-body
hook reads. Issues are filed from Python (`propose --apply`), past the hook.
The upstream retro also comments on issues.

## Decision

- **A run reads back each PR, issue and comment it creates**, after waiting
  for it to settle (10 seconds by default, `--settle`), since the footer may
  be added after the write returns, and compares the body GitHub holds with
  the body it sent, ignoring CRLF line ends and trailing space.
  - Identical: done.
  - The body sent plus exactly the platform footer at the end (the session
    link, with or without its rule; a body that itself ends with a rule keeps
    it): the run writes the body it sent back, waits again, reads again, and
    requires it identical.
  - Anything else: it fails, and repairs nothing in that body. It never
    guesses which part of a changed body is its own.
  - The body sent holding a run reference fails too, before any wait, read
    or write, and is never written back.
  When several bodies are read back together, every one is checked and
  every footer found is taken off before the run fails; one error then
  names each PR, issue or comment that failed. Errors never quote a body.
- **`trimtab verify-body`** does it for a PR (`--pull N`, the number the POST
  returned), an issue (`--issue N`) or a comment
  (`--comment ID`), against `--body-file` or `--body`. Exit 0 is the body
  sent, and says when it took the footer off; 1 is any other change, or a
  footer that came back; 2 is that it could not read or write. Every call is
  repository-scoped REST (ADR 0021).
- **The commands chain it after the POST**, on the same command line
  (`N=$(gh api -X POST … --jq .number) && trimtab verify-body … --pull "$N"`),
  so it runs only when the PR was created and cannot be forgotten as a later
  step. The PR-body hook still reads the POST inside the substitution. A static test fails if
  a shipped file POSTs a PR or a comment without it.
- **`propose --apply` reads back every issue it files**, together, after
  filing them all: one shared wait, then one more only if a footer was taken
  off, however many issues there are. Issues are filed only inside the
  sink's `filing()` block, which reads back everything filed in it on
  leaving, however it is left, so no caller can file and skip the read-back.
  It lists the issues it opened and the IDs it did not try. It exits 1 when
  an issue's body is wrong, when one could not be read back, or when a
  create failed in a way that may have filed it (a server error, a timeout,
  an unexpected answer): a re-run would skip that issue and never read it.
  It exits 2 only when GitHub refused the create (a 4xx), which filed
  nothing, so a re-run is safe.
- **Comparing is a value, failing is the boundary's.** `compare` returns
  SAME, FOOTER or DIFFERS; `verify_body` raises only to stop the run.
- **The write-back is authorised**: each routine prompt and command lists
  writing back the body the run sent, to take the footer off, among the
  writes the run may make.

## Options considered

- **The settings alone (ADR 0022's first part).** Rejected as sufficient: the
  trial shows the footer survives `sessionUrl: false`.
- **`attribution: false` in the installed settings.** Taken as well, as its
  own control change: whether it stops the footer is a trial of that change.
  This one does not depend on it, and stays useful if it does not.
- **Routines push branches only, and the operator opens each PR.** Rejected:
  it gives up the routines' output for a leak this change bounds. Kept as the
  fallback if a footer cannot be taken off.
- **Open the PR through `trimtab` instead of `gh api`.** Rejected: the
  PR-body hook reads `gh api` POSTs, so the body would reach GitHub unread by
  the hook. Here the hook still checks every body, and the write-back only
  ever restores text the hook already passed.
- **Find the PR by its head branch.** Rejected: one more call, and a listing
  read milliseconds after the create may not show it yet; the POST already
  returns the number.
- **Read back at once, with no wait.** Rejected: a footer added a moment
  after the write would be missed and the run would report clean.
- **Take the footer off without reading back again.** Rejected: if the
  platform appends it on every write, a run would report a clean body that is
  not.
- **Strip whatever follows the `🤖 Generated with` line.** Rejected: it
  would delete text it does not recognise, which may be the next thing to
  investigate.
- **Read the HTTP status from `gh api --include`** to tell a refused create
  (4xx, nothing filed) from one that may have filed the issue. Rejected for
  now: gh gives the status only in its error text (`gh: Validation Failed
  (HTTP 422)`) unless every call switches to `--include` and parses the
  status line and headers ahead of the body, a change to all of `GhApi`.
  The 404 check already reads the same text. The text match is a deviation
  from the reliability rule's preference for explicit error categories,
  taken because a misread fails safe: a status it cannot find reads as "may
  have been filed", which stops the run (exit 1) rather than inviting a
  re-run. Tests pin the forms read. Revisit if gh changes them, or when
  `GhApi` needs the status for another reason.

## Consequences

- A PR, issue or comment a run creates holds, once the run has finished, the
  body it sent, or the run has failed and said which one is wrong.
- Accepted: GitHub keeps a body's earlier versions in its edit history, so
  the footer's session link stays there, visible to anyone who can read the
  repository, until the platform stops adding it. Removing an edit-history
  entry is the operator's job on GitHub, not the run's.
- Accepted: between the POST and the write-back, the footer is live for
  about the settle time; a notification or a webhook sent in that window
  carries it. Each PR, issue or comment costs the run up to two waits.
- Accepted: the footer is matched by its exact form. A changed form fails
  the run (exit 1) rather than passing; the pattern is then updated.
- Accepted: a footer the platform adds later than the settle time is not
  seen. `check-pr` in a consumer's CI is the remaining check, and the trial
  records when the footer appeared.
- The comparison ignores CRLF line ends and trailing space, which GitHub may
  change; any other difference fails.

## Trial, still open

After this change is on the pinned base: one manual run of a per-project
routine that opens a PR. Its log shows `trimtab verify-body` exit 0, and its
PR's body, read afterwards, holds no session link or footer. Record here
whether the footer was there to take off.
