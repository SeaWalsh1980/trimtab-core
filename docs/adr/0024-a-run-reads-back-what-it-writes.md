# 0024. A run reads back what it writes

## Context

ADR 0022's trial (2026-10-14) ran a per-project routine on a base whose
installed settings carry `"attribution": {"sessionUrl": false}`. The commit
had no `Claude-Session:` trailer and the bare session URL line was gone, so
the setting was read. The PR body was not clean: after the body the run sent,
which ended at its `🤖 Generated with` line and passed `trimtab check-pr`,
GitHub held two more lines, a `---` rule and
`_Generated by [Claude Code](https://claude.ai/code/session_…)_`.

Claude Code's settings reference says `sessionUrl: false` also omits the link
in pull request descriptions. It did not omit this one, and no documented
setting names it: `attribution.pr` sets the line Claude Code writes, which the
run writes itself. Which component appends the footer is not documented. The
operator reported it upstream. A server-managed (organisation) setting is the
only documented route into a multi-repository cloud session, and nothing
documents it covering this footer either.

Every PR a run opens goes through `gh api` POST to `pulls`, which the PR-body
hook reads. Issues are filed from Python (`propose --apply`), past the hook.
The upstream retro also comments on issues.

## Decision

- **A run reads back each PR, issue and comment it creates**, after waiting
  for it to settle (10 seconds by default, `--settle`), since the footer may
  be added after the write returns, and compares the body GitHub holds with
  the body it sent, ignoring CRLF line ends and trailing space.
  - Identical: done.
  - The body sent plus exactly the platform footer at the end (the session
    link, with or without its rule; a body that itself ends with a rule keeps
    it): the run writes the body it sent back, waits again, reads again, and
    requires it identical.
  - Anything else: it fails, and repairs nothing in that body. It never
    guesses which part of a changed body is its own.
  - The body sent holding a run reference fails too, before any wait, read
    or write, and is never written back.
  When several bodies are read back together, every one is checked and
  every footer found is taken off before the run fails; one error then
  names each PR, issue or comment that failed. A GitHub error reading or
  writing one body does not stop the others either: alone, it is raised as
  it came once the rest are done; with a body that failed, both are named
  in one error. Errors never quote a body.
- **An interrupt is not held up.** Ctrl-C inside the filing block skips the
  wait and the read-back and goes on at once, with a note naming each issue
  filed so far, to check with `trimtab verify-body`.
- **`trimtab verify-body`** does it for a PR (`--pull N`, the number the POST
  returned), an issue (`--issue N`) or a comment
  (`--comment ID`), against `--body-file` or `--body`. Exit 0 is the body
  sent, and says when it took the footer off; 1 is any other change, or a
  footer that came back; 2 is that it could not read or write. (Amended
  2026-10-15: the platform's generic footer, on the first read or after the
  write-back, is exit 0 too; see "The generic footer is accepted" below.)
  Every call is repository-scoped REST (ADR 0021).
- **The commands chain it after the POST**, on the same command line
  (`N=$(gh api -X POST … --jq .number) && trimtab verify-body … --pull "$N"`),
  so it runs only when the PR was created and cannot be forgotten as a later
  step. The PR-body hook still reads the POST inside the substitution. A static test fails if
  a shipped file POSTs a PR or a comment without it. (Amended 2026-10-28: for
  a body sent from a file, the read-back is a command of its own; see "The
  read-back is a command of its own" below.)
- **`propose --apply` reads back every issue it files**, together, after
  filing them all: one shared wait, then one more only if a footer was taken
  off, however many issues there are. Issues are filed only inside the
  sink's `filing()` block, which reads back everything filed in it on
  leaving, however it is left, so no caller can file and skip the read-back.
  It lists the issues it opened and the IDs it did not try. It exits 1 when
  an issue's body is wrong, when one could not be read back, or when a
  create failed in a way that may have filed it (a server error, a timeout,
  an unexpected answer): a re-run would skip that issue and never read it.
  It exits 2 only when GitHub refused the create (a 4xx), which filed
  nothing, so a re-run is safe.
- **Comparing is a value, failing is the boundary's.** `compare` returns
  SAME, FOOTER or DIFFERS (and, by the amendments below, GENERIC,
  IN_PLACE and IN_PLACE_GENERIC); `verify_body` raises only to stop the run.
- **The write-back is authorised**: each routine prompt and command lists
  writing back the body the run sent, to take the footer off or restore the attribution line
  it replaced (amendment, 2026-10-17), among the
  writes the run may make.
- **The generic footer is accepted** (amendment, 2026-10-15). The same line
  linking `https://claude.ai/code` with no session, with or without its rule,
  matched by its exact form:
  - after a write-back, it passes in place of the body sent (`REPLACED`);
  - on the first read, it is left alone (`GENERIC`): it names nothing, and a
    write would only bring it back.
  Both exit 0 and say so. The session footer coming back after the
  write-back still fails, as does any other link or text.
- **A footer in place of the attribution line is written back** (amendment,
  2026-10-17). A consumer project's retro draft PR came back with its last line,
  `🤖 Generated with [Claude Code](https://claude.com/claude-code)`, replaced
  by the session footer: not after the body, in place of part of it.
  `verify-body` read that as a change, exited 1, and the run stopped with the
  session link left in the PR until the operator edited it. Opening the fix
  for this showed the same on three more PRs; editing each body afterwards
  restored the line and added no footer.
  - Either footer standing exactly where the attribution line was is
    `IN_PLACE` (session link) or `IN_PLACE_GENERIC`, and is always written
    back, so the report says whether a session link was published: it has
    deleted text the run sent, so leaving the generic form alone, as on the
    first read after the body, would lose the line.
  - After the write-back, the body must be as sent, or as sent with the
    generic footer after it (`IN_PLACE_REPLACED` or `IN_PLACE_GENERIC_KEPT`,
    by which footer stood in place). A footer in place of the line again
    fails.
  - The line is one constant, `ATTRIBUTION_LINE`, matched only as a whole
    line; tests hold every command and routine prompt to it.
  - Only that one line, matched by its exact text, is recognised. A footer
    in place of any other text is a difference. This is not the rejected
    "strip whatever follows the `🤖 Generated with` line" below: nothing
    unrecognised is deleted, and the write-back restores the line.
- **The read-back is a command of its own** (amendment, 2026-10-28). A
  consumer project's conformance routine pushed its report branch and opened
  no PR: guard-github refused the chained command, because it reads a request
  file before the command runs and refuses one whose name appears anywhere
  else in the command (ADR 0037), and `--body-file` names it a second time.
  The retro's identical chain had passed only because its run wrote the path
  as a variable, which the guard does not read (ADR 0037, Residuals).
  - A command that sends a body from a file (`-F body=@<file>`) only creates:
    `gh api -X POST … --jq .number` prints the number. Once it has, the run
    reads back with `trimtab verify-body --repo "$REPO" --pull <N>
    --body-file <file>` as a command of its own, the number written out.
    The exit codes are read as before.
  - A body given inline (`-f body="…"` with `--body "…"`) names no file, and
    its chain stays as it was.
  - The static test holds the read-back to the same step: later on the
    POST's command line, or in a later command before a blank line, the next
    list item or a code fence ends the step. It counts only a call with
    options that reads back the same kind (`--pull` for a PR, `--comment` for
    a comment), so a prose mention, a shell comment or another write's
    read-back does not satisfy it. A second test fails any command line that
    names one body file both as `body=@` and as `--body-file`, so the chain
    guard-github refuses cannot come back, with the path written out or as a
    variable.

## Options considered

- **The settings alone (ADR 0022's first part).** Rejected as sufficient: the
  trial shows the footer survives `sessionUrl: false`.
- **`attribution: false` in the installed settings.** Taken as well, as its
  own control change: whether it stops the footer is a trial of that change.
  This one does not depend on it, and stays useful if it does not.
  (2026-10-14: that change landed as
  `{"commit": "", "pr": "", "sessionUrl": false}`, not `false`; see ADR
  0025.)
- **Routines push branches only, and the operator opens each PR.** Rejected:
  it gives up the routines' output for a leak this change bounds. Kept as the
  fallback if a footer cannot be taken off.
- **Open the PR through `trimtab` instead of `gh api`.** Rejected: the
  PR-body hook reads `gh api` POSTs, so the body would reach GitHub unread by
  the hook. Here the hook still checks every body, and the write-back only
  ever restores text the hook already passed.
- **Find the PR by its head branch.** Rejected: one more call, and a listing
  read milliseconds after the create may not show it yet; the POST already
  returns the number.
- **Read back at once, with no wait.** Rejected: a footer added a moment
  after the write would be missed and the run would report clean.
- **Take the footer off without reading back again.** Rejected: if the
  platform appends it on every write, a run would report a clean body that is
  not.
- **Strip whatever follows the `🤖 Generated with` line.** Rejected: it
  would delete text it does not recognise, which may be the next thing to
  investigate.
- **Read the HTTP status from `gh api --include`** to tell a refused create
  (4xx, nothing filed) from one that may have filed the issue. Rejected for
  now: gh gives the status only in its error text (`gh: Validation Failed
  (HTTP 422)`) unless every call switches to `--include` and parses the
  status line and headers ahead of the body, a change to all of `GhApi`.
  The 404 check already reads the same text. The text match is a deviation
  from the reliability rule's preference for explicit error categories,
  taken because a misread fails safe: a status it cannot find reads as "may
  have been filed", which stops the run (exit 1) rather than inviting a
  re-run. Tests pin the forms read. Revisit if gh changes them, or when
  `GhApi` needs the status for another reason.
- **Fail on the generic footer too** (as first decided). Rejected after the
  first trial: the platform adds it to every edit, so no run that writes a
  body could exit 0, and every routine would stop at its first PR for text
  that names nothing.
- **Write back until no footer is left.** Rejected: each write brings the
  generic footer back, so it never ends; each attempt is one more edit in the
  history and one more notification.
- **Fall back to routines that push branches only.** Not needed: it was kept
  for a footer that could not be taken off, and the one that stays names
  nothing.
- **Keep the chain and write the body path as a variable** (2026-10-28).
  Rejected: it passes only through a gap guard-github records as a residual;
  closing the gap would break every command again, and the commands would be
  written to rely on a guard not reading them.
- **Let guard-github pass a file the read-back names** (2026-10-28).
  Rejected for this change: the guard is a security control, changed only by
  the operator, and the refusal exists because a later word in the command
  can rewrite the file before gh reads it. Telling a harmless second name
  from a rewrite is the guard's own decision to make, not the commands'.
- **Pipe the number into the read-back** (`… --jq .number | xargs …`).
  Rejected: guard-github refuses gh run under `xargs`, and a pipe still puts
  both names in one command.

## Consequences

- A PR, issue or comment a run creates holds, once the run has finished, the
  body it sent, or the run has failed and said which one is wrong. (Amended
  2026-10-15: or that body followed by the platform's generic footer; see
  Decision.)
- Accepted: GitHub keeps a body's earlier versions in its edit history, so
  the footer's session link stays there, visible to anyone who can read the
  repository, until the platform stops adding it. Removing an edit-history
  entry is the operator's job on GitHub, not the run's.
- Accepted: between the POST and the write-back, the footer is live for
  about the settle time; a notification or a webhook sent in that window
  carries it. Each PR, issue or comment costs the run up to two waits.
- Accepted: the footer is matched by its exact form. A changed form fails
  the run (exit 1) rather than passing; the pattern is then updated.
- Accepted: a footer the platform adds later than the settle time is not
  seen. `check-pr` in a consumer's CI is the remaining check, and the trial
  records when the footer appeared.
- The comparison ignores CRLF line ends and trailing space, which GitHub may
  change; any other difference fails.
- Accepted (2026-10-15): every PR, issue and comment a run creates keeps the
  platform's generic footer after its own closing line. It links Claude
  Code's site, not the run.
- Accepted (2026-10-28): a read-back that is a command of its own is no
  longer tied to the create by `&&`. The command's text tells the run to run
  it once the create has printed a number, and the static test keeps it in
  the same step, but nothing in the shell stops a run that skips it.
  `check-pr` in a consumer's CI remains the check after the fact.
- Accepted (2026-10-28): the number is written out by hand. A wrong number
  reads back another PR, whose body is not the one sent, so `verify-body`
  exits 1 and the run stops; it writes back only a body that is the one sent
  plus a footer, so it does not edit that PR.

## First trial (2026-10-15)

One manual run of a per-project conformance routine, on a base carrying this
change and ADR 0025's settings, opened a draft PR through the chained POST.

- `trimtab check-pr` passed the body before it was sent.
- The PR as created held the body sent, then a `---` rule and the session
  footer (`_Generated by [Claude Code](https://claude.ai/code/session_…)_`).
  It was there when the run read back, after the 10-second wait.
- The run wrote back the body sent. The platform added a `---` rule and
  `_Generated by [Claude Code](https://claude.ai/code)_` to that edit: the
  same line, linking no session.
- `verify-body` exited 1 ("the platform's footer came back after the body
  sent was written again"), and the run stopped and reported it, as told.
- The edit history holds both versions; the session link is in the first.

Result: failed. The session link was taken off, but the rule as written
required the body sent exactly. Amended as recorded under Status and
Decision. The trial is run again on a base carrying the amendment, with the
check under "Trial, still open" as amended.

## Second trial (2026-10-15 and 2026-10-16)

Two manual runs of per-project routines on a base carrying the amendment and
ADR 0025's settings, each with its guards live: a retro (2026-10-15), which
opened a draft PR and an issue, and a conformance review (2026-10-16), which
opened a draft PR.

- Each PR as created held the body sent, then a `---` rule and the session
  footer.
- Each run wrote back the body sent; the platform added its generic footer to
  that edit. `verify-body` exited 0 on both, reporting the session footer
  removed, the generic footer in its place, and GitHub's edit history still
  holding the session footer (`REPLACED`).
- Each PR's body, read afterwards, held the body sent and then only the
  generic footer: no session link. The commits and the bodies' checks before
  sending are recorded in ADR 0022, "Second trial result".
- The issue, created by `propose --apply`, held the generic footer from its
  creation, with no session footer to take off; it was left alone.

Result: passed. The footer there to take off was the session footer, on both
PRs; the generic footer stayed. The edit history of both PRs keeps the
session footer, as the Consequences accept.
